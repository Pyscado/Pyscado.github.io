title: Tool Mania

---

While working as a detection engineer in a large organization, I was tasked with creating actionable alerts and detections from a fragmented and massive tech stack. If you have worked at any mid to large sized company you likely have encountered tech debt from the ghost of engineer’s past. In my case, this tech debt manifested as three SIEMs, three EDRs, several AVs, numerous firewalls, and more IDS/IPS systems than I can even say. Many rushed acquisitions resulted in poorly formatted or incomplete logging.  This really is a tale as old as time. How does one meet leadership expectations of MITRE coverage without contributing to alert fatigue of the SOC analysts in such a large stack?

Every organization I have been a part of walks a fine line of collecting enough logs to find meaningful data and collecting so many logs that the value gets lost. Frequently, tools are purchased to try to fix issues with logging. Tools can be useful for parsing data, they come with out of the box alerts, promises that they will fix every issue you can think of, and they have nice shiny interfaces. There is a time and a place for tools to be sure, but there is a point of diminishing returns on them. Having multiple tools that parse the same data leads to confusion. Each tool vendor wants their tool to be the main hub for a SOC, they build the tool with the expectation that you will be using their solution as your primary pane of glass. Because each vendor expects to be the primary, they often add meta data (risk score, severity, TTP numbers) that conflicts with other products in the same environment. For example, an alert with a CRITICAL severity in the IDS might show as MEDIUM in the NDR. This issue becomes exasperated when you have multiple versions of the same product, two different firewall solutions or three different EDRs, all picking up on the same information but not reaching the same conclusion.

So, what do we do about this problem of too many products and low logging quality? Well, the answer depends on several factors so your mileage may vary. In my experience, once a tool has been purchased there is an expectation that it will fix problems and fill gaps. This is only half of the story, new tools come with new problems. Log forwarders need to be constructed, new integrations have to be built to fit it into the CI/CD pipeline, automation needs to tap into the product, vendor detections need to be reviewed, the list goes on and on. Before selecting a tool, be sure to consider these new tasks that will arise, can those tasks be justified with the gap that the tool fills? Another issue I have seen many times is not fully using a product. There have been so many cases where a tool is purchased to fill a gap that another tool (already installed and paid for) *could* be filling. It's unlikely that SIEM A is going to have gaps that require SIEM B to be run in parallel. Obviously, there is going to be overlap when moving from one product to another but having two solutions for extended periods of time is not ideal. Make sure you are using the tool to its full potential before buying another.

When I create alerts, if the environment is too messy and filled with tools, I find myself relying on more basic log sets. Having data like Windows Event Logs, Proxy, and other raw telemetry can be a gold mine for creating detections. When faced with a towering tech stack, sometimes it is easier to go back to the basics and write detections that focus on the largest set of devices as possible. I am a big fan of Windows Event Logs for that reason, they are simple to enable and the detections will apply to any Windows based environment.

The other direction to go is correlation. Maybe it's too late to walk back the number of tools at your company, when this happens you can create generic data from the tools. For example, all IDS/IPS should have the same basic information, source, destination, and positive signature match. Instead of having an alert for IDS 1 and a separate alert for IDS 2, feed the data into the same model where the fields are normalized. All the of the sources, destinations, etc. are formatted the same. This way you can search across all of your data at the same time in the same location cutting down on the context switching between products that the analysts would have to do.

The best piece of advice I could give for crowded tech stacks is, less is more. In my experience the biggest obstacle for achieving unified and concise tooling/logging is acquisitions. When an existing entity is purchased, the goal is to fold them into the parent company and get them operational as quickly as possible. This is where policies come into play. Part of the acquisition process should include log formatting/forwarding, and a plan to move them over to the security products that the parent company is using. There might be some time where existing product licenses need to expire and that is ok. Part of the onboarding for that new company must include those expectations, the company must not be considered onboarded until the logging and monitoring requirements are met. This does not mean the new subsidiary is non-operational, it just means that the end date for the acquisition to be fully checked off is a little further out.

More tools does not mean more coverage, it means more expenses, more things to troubleshoot, more engineers required, and data being parsed more than once. Keep your stack clean, do not over purchase, maximize the value you can with your existing tools
